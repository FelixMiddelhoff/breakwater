# BW004: AlterColumn narrows the column and can fail or rewrite the table

`migrationBuilder.AlterColumn(...)` that changes the CLR type, or narrows length,
precision or scale compared to the `old*` arguments EF Core generates, can truncate
or reject existing values, and many providers rewrite the whole table to apply it.

## Why it hurts

- Narrowing a type, length, precision or scale can truncate or reject data already
  in the table.
- Many providers rewrite the whole table (and its indexes) to apply the change,
  holding a lock for the duration.
- EF Core compares old and new metadata itself and passes both to `AlterColumn`, so
  Breakwater uses those `old*` values directly: widening a column (`varchar(50)` to
  `varchar(100)`) never fires.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // breakwater: expect BW004
    migrationBuilder.AlterColumn<string>(
        name: "Description",
        table: "Products",
        maxLength: 50,
        oldMaxLength: 500);
}
```

## Safe alternative

Add a new column with the desired type/length, backfill it in batches, switch the
application code to the new column, then drop the old one in a later migration.

## When it is fine

Lower the severity in `.editorconfig`:

```ini
dotnet_diagnostic.BW004.severity = suggestion
```

## Not reported

- Widening a column (new length/precision/scale is greater than or equal to the
  old one), since narrowing is what actually risks existing data.
- A column on a table created earlier in the same migration (`CreateTable`): it is
  still empty.
- Either side's CLR type, length, precision or scale unknown: the comparison needs
  both values, per "silent when unsure".
- This rule shares one `AlterColumn` call with BW005, BW015 and BW026: only the
  most specific of the four is reported for the same call.
