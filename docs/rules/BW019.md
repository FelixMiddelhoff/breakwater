# BW019: raw SQL on PostgreSQL builds an index, locks a table, or rewrites a table under lock

The same class of risk as BW007 (unsafe index build) and BW004 (unsafe type
change), but hidden inside `migrationBuilder.Sql(...)` on Postgres, where those
rules never see it: a `CREATE INDEX` without `CONCURRENTLY`, `LOCK TABLE`,
`VACUUM FULL`, or `ALTER TABLE ... SET DATA TYPE`.

## Why it hurts

Raw SQL bypasses `migrationBuilder`'s own operations, so Breakwater cannot see the
risk unless it looks at the SQL text itself. These statements hold a lock for
longer than they need to, or rewrite the table.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    if (migrationBuilder.IsNpgsql())
    {
        // breakwater: expect BW019
        migrationBuilder.Sql("CREATE INDEX IX_Orders_CustomerId ON \"Orders\" (\"CustomerId\")");
    }
}
```

## Safe alternative

Use `CREATE INDEX CONCURRENTLY` (outside a transaction, `suppressTransaction:
true`) instead of a plain `CREATE INDEX`; avoid `LOCK TABLE` and `VACUUM FULL`
inside a migration; run a type change outside the migration's transaction.

## When it is fine

Lower the severity in `.editorconfig`:

```ini
dotnet_diagnostic.BW019.severity = suggestion
```

## Not reported

- The call is not inside a known `if (migrationBuilder.IsNpgsql())` guard: provider
  unknown, silent per "silent when unsure".
- The SQL text is not a compile-time constant.
- None of the risky statement shapes above are present.

This rule reuses the same SQL tokenizer as BW010 but a different keyword set, so a
single raw-SQL call can trigger both independently.
