# BW030: AddForeignKey with onDelete: Cascade

`migrationBuilder.AddForeignKey(..., onDelete: ReferentialAction.Cascade)` means
deleting one parent row also removes every matching child row.

## Why it hurts

A cascade delete can silently remove far more data than the person running the
delete expected, and SQL Server rejects a schema with more than one cascade path
into the same table at runtime.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // breakwater: expect BW030
    migrationBuilder.AddForeignKey(
        name: "FK_Orders_Customers",
        table: "Orders",
        columns: new[] { "CustomerId" },
        principalTable: "Customers",
        onDelete: 1 /* ReferentialAction.Cascade */);
}
```

## Safe alternative

Confirm cascading is really intentional; consider `ReferentialAction.Restrict` and
deleting children explicitly in application code instead.

## When it is fine

This rule is **off by default** in every profile except `strict`, because cascade
delete is EF Core's own default for a required relationship and is far too common
to warn on by default. Enable it with:

```ini
breakwater_profile = strict
```

Once enabled, lower it like any other rule:

```ini
dotnet_diagnostic.BW030.severity = suggestion
```

## Not reported

- Under the default `recommended` profile, this rule never reports.
- `onDelete` is not `Cascade` (or is not set at all).
