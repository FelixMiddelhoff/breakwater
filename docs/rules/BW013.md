# BW013: migration mixes a schema change with a data change

A migration whose `Up` method has both a schema operation (for example
`AddColumn`) and a data operation (`InsertData`/`UpdateData`/`DeleteData`) holds
the schema change's lock for the whole data change too, not just the schema part.

## Why it hurts

One migration, one transaction: the schema lock is held for as long as the data
change takes, even though the two are logically separate.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.AddColumn<string>(name: "Region", table: "Customers", nullable: true);

    // breakwater: expect BW013
    migrationBuilder.UpdateData(
        table: "Customers",
        keyColumn: "Id",
        keyValues: new object[] { 1 },
        column: "Region",
        values: new object[] { "EU" });
}
```

## Safe alternative

Split the schema change and the data change into separate migrations so each
holds its lock for as little time as possible.

## When it is fine

This is a Suggestion-tier rule (`Info` severity, IDE hint only, no build output) by
default. Raise it if you want it to fail the build:

```ini
dotnet_diagnostic.BW013.severity = warning
```

## Not reported

The migration has only a data operation, or only a schema operation, not both.
