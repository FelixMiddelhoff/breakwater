# BW014: AlterColumn changes a provider-specific type

On PostgreSQL, an `AlterColumn` that changes between two non-primitive CLR types -
the shape a mapped Postgres enum change takes - can fail or force a table rewrite
inside the migration's transaction, depending on the provider version.

## Why it hurts

Changing the CLR type behind a mapped Postgres type happens inside the migration's
own transaction; depending on the Npgsql version this can fail outright or force a
table rewrite that holds a lock.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    if (migrationBuilder.IsNpgsql())
    {
        // breakwater: expect BW014
        migrationBuilder.AlterColumn<OrderStatusV2>(
            name: "Status",
            table: "Orders",
            oldClrType: typeof(OrderStatusV1));
    }
}

public enum OrderStatusV1 { Open, Closed }
public enum OrderStatusV2 { Open, Fulfilled, Closed }
```

## Safe alternative

Verify the generated SQL for your Npgsql version and, if needed, run the type
change outside the migration's transaction (raw SQL with
`suppressTransaction: true`, or a separate deploy step).

## When it is fine

This is a Suggestion-tier rule (`Info` severity, IDE hint only, no build output) by
default. Raise it if you want it to fail the build:

```ini
dotnet_diagnostic.BW014.severity = warning
```

## Not reported

- The call is not inside a known `if (migrationBuilder.IsNpgsql())` guard: provider
  unknown, silent per "silent when unsure".
- Either the old or the new CLR type is unknown, or they are the same type.
- Either type is a built-in .NET primitive (`string`, `int`, `System.Guid`, ...):
  a primitive-to-primitive change is BW004's job, not this rule's.
- This rule deliberately can co-fire with BW004 on the same call: it is a
  different aspect of the same change, not a duplicate finding.
