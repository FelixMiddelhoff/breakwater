# BW010: raw SQL runs an unfiltered UPDATE/DELETE, a TRUNCATE, or a DROP

`migrationBuilder.Sql(...)` is analyzed statement by statement: a `TRUNCATE` or
`DROP` anywhere, or a leading `UPDATE`/`DELETE` with no `WHERE` clause (or only
`WHERE 1=1`), holds a lock and a long transaction against the whole table.

## Why it hurts

A statement like this touches every row (or drops the object outright), which can
cause replication lag and lock escalation on a large table.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // breakwater: expect BW010
    migrationBuilder.Sql("UPDATE Orders SET Status = 'Archived'");
}
```

## Safe alternative

Batch the change outside the migration, or in chunks with its own `WHERE` clause
per batch (for example by primary key range).

## When it is fine

Lower the severity in `.editorconfig`:

```ini
dotnet_diagnostic.BW010.severity = suggestion
```

## Not reported

- `UPDATE`/`DELETE` with a real `WHERE` clause (`WHERE 1=1 AND ...` counts as a
  real condition; the exact trivial `WHERE 1=1`/`WHERE 1 = 1` does not).
- The SQL text is not a compile-time constant (a variable, `File.ReadAllText`, a
  resource): unknown content is not analyzed, per "silent when unsure". Constant
  interpolation and concatenation of constants across lines are still followed.
- Keywords that appear only inside a string literal or a comment in the SQL text.

Each statement in a multi-statement `Sql(...)` call is checked on its own, but only
the first unsafe statement found is reported.
