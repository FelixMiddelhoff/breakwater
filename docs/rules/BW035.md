# BW035: raw SQL disguises a structural schema change

`migrationBuilder.Sql(...)` is tokenized and scanned for an `ALTER TABLE`
statement that carries a `DROP COLUMN` (the same data-loss risk BW001 catches
for the typed API), or an `ADD COLUMN ... NOT NULL` with no `DEFAULT` (the
same risk BW006 catches) - both invisible to BW001/BW006 because they only
look at typed `MigrationBuilder` calls, never at DDL text inside a string.

Real-world pattern this rule was built for: bitwarden-mysql's
`GrantIdWithIndexes.cs`, which does
`ALTER TABLE `Grant` DROP COLUMN `Id`` then
`` ALTER TABLE `Grant` ADD COLUMN `Id` INT AUTO_INCREMENT UNIQUE `` inside a
raw SQL stored procedure body - a real column drop/rebuild that never went
through `DropColumn`/`AddColumn`.

## Why it hurts

Same as BW001/BW006: dropping a column loses its data, and an old application
version still reading it during a rolling deploy breaks; adding a column
`NOT NULL` with no default fails outright on a non-empty table. Hiding either
one inside a SQL string does not remove the risk, it just hides it from the
tool (and from a reviewer skimming the typed calls in the migration).

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // breakwater: expect BW035
    migrationBuilder.Sql("ALTER TABLE `Grant` DROP COLUMN `Id`");
}
```

## Safe alternative

Use the typed API instead (`migrationBuilder.DropColumn(...)` /
`migrationBuilder.AddColumn<T>(...)`) so BW001/BW006 can see the change and
point at the safe expand/contract sequence. If the raw SQL is unavoidable,
apply the same sequence by hand: stop using the column, deploy, drop it in a
later migration; or add the column nullable, backfill, then constrain it.

## When it is fine

Suppress it for a specific call with a reason once you have confirmed the
sequencing is safe (for example, deploy is not rolling and nothing reads the
dropped column):

```csharp
// breakwater: allow BW035 downtime deploy, column unused since v3
migrationBuilder.Sql("ALTER TABLE `Grant` DROP COLUMN `Id`");
```

Or lower the severity in `.editorconfig`:

```ini
dotnet_diagnostic.BW035.severity = suggestion
```

## Not reported

- Any `ALTER TABLE` shape other than `DROP COLUMN` or `ADD COLUMN ... NOT
  NULL` with no `DEFAULT` - a `RENAME COLUMN`, a type change, or an `ADD
  COLUMN` that is nullable or carries a `DEFAULT`, are out of this rule's
  declared scope (some of those shapes are covered by other rules; a nullable
  or defaulted `ADD COLUMN` is the same safe shape BW006 stays silent on).
- The SQL text is not a compile-time constant: unknown content is not
  analyzed, per "silent when unsure".
- Keywords that appear only inside a string literal or a comment in the SQL
  text.
- This rule does not attempt to determine whether the dropped column's data
  was backed up or copied elsewhere first (that would need tracking data flow
  across statements, which the tokenizer does not do) - it always flags an
  `ALTER TABLE ... DROP COLUMN`, the same way BW001 always flags a typed
  `DropColumn` call regardless of what happens around it.

## Overlap with other raw-SQL rules

BW010 also matches an `ALTER TABLE ... DROP COLUMN` statement (it flags any
statement containing a `DROP` keyword), but with a vaguer message. BW035 is
strictly more specific for this shape, so it suppresses BW010 for the same
statement (most-specific-wins, the same pattern already used for BW023 over
BW001) - only BW035 is reported, not both. BW019 (Postgres-specific raw SQL),
BW031 (batch separators), BW033 (secrets) and BW034 (disabled safety checks)
look for different keywords/shapes and do not collide; if one of them also
fires on the same raw SQL string, that is a genuinely different problem and
both are reported, the same way BW010 and BW034 both fire on a `DROP
DATABASE` statement.
