# BW029: migration has no transaction to roll back to on failure

Either `SuppressTransaction` is set, or the migration targets MySQL (where DDL
statements each commit on their own): if any operation after the first fails, the
earlier ones already happened and there is no transaction to roll back.

## Why it hurts

A failure partway through leaves the database half migrated, in a state that
matches neither the old nor the new migration - with nothing to undo the
operations that already succeeded.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.SuppressTransaction = true;
    // breakwater: expect BW029
    migrationBuilder.AddColumn<string>(name: "Nickname", table: "Users", nullable: true);
    migrationBuilder.AddColumn<string>(name: "Bio", table: "Users", nullable: true);
}
```

## Safe alternative

Keep migrations with several operations small, and verify each one individually
before combining them, so a failure partway through is easy to reason about and
fix by hand.

## When it is fine

This is a Suggestion-tier rule (`Info` severity, IDE hint only, no build output) by
default. Raise it if you want it to fail the build:

```ini
dotnet_diagnostic.BW029.severity = warning
```

## Not reported

- The migration has one operation or fewer.
- `SuppressTransaction` is not set and the migration is not guarded by
  `if (migrationBuilder.IsMySql())`.

This rule fires once per migration, on the first recognized operation - not once
per operation in the method.
