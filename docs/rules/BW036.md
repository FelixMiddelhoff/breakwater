# BW036: raw SQL drops and immediately redefines a procedure, function, or view

`DROP PROCEDURE`/`FUNCTION`/`VIEW IF EXISTS <name>` immediately (or later,
still within the same `Sql(...)` call) followed by `CREATE [OR REPLACE]
PROCEDURE`/`FUNCTION`/`VIEW` of the **same name and kind** is a recognized,
intentional idempotent-redefinition idiom - seen twice in the real corpus
(bitwarden-mysql's `GrantIdWithIndexes.cs`, platformplatform's
`AddFeatureFlagsSchema.cs`) - and is materially lower risk than an unpaired
`DROP`, which is redefining the object, not removing it.

## Design note

This is a refinement of BW010's "DROP always flags" behavior, but shipped as
its own rule id rather than a hidden branch inside BW010: it gets its own
message, its own (lower) severity, and its own doc page and tests, the same
way every other "a more specific rule supersedes a general one" case in this
codebase works (BW023 over BW001, BW026/BW005/BW004 sharing `AlterColumn`).
BW010's own contract - "DROP always flags" - is unchanged for every other
shape (tables, columns, indexes, an unpaired procedure/function/view drop);
only this specific DROP-IF-EXISTS-then-CREATE-same-object pairing is
downgraded, by BW036 suppressing BW010 for that statement (most-specific-wins).

## Why it hurts less than an unpaired DROP

An unpaired `DROP` (BW010) removes an object with no way back. A `DROP ...
IF EXISTS` immediately followed by a matching `CREATE` is redefining that
same object - the net effect (assuming the `CREATE` succeeds) is that the
object still exists afterward, just with new logic. It is still worth
knowing about (the object is briefly gone mid-migration, so nothing should
call it in that window), which is why this is Suggestion, not silent.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // breakwater: expect BW036
    migrationBuilder.Sql(@"
        DROP PROCEDURE IF EXISTS Grant_UpdateId;
        CREATE PROCEDURE Grant_UpdateId() BEGIN SELECT 1; END");
}
```

## Safe alternative

No change needed for the idiom itself; it is already the recommended,
re-runnable pattern. If the object is called from application code, make
sure nothing calls it while the migration is running.

## When it is fine

Lower the severity further, or suppress with a reason, the same as any other
rule:

```ini
dotnet_diagnostic.BW036.severity = silent
```

## Not reported / stays as plain BW010 instead

- An unpaired `DROP PROCEDURE`/`FUNCTION`/`VIEW` with no matching `CREATE`
  later in the same `Sql(...)` call - reports BW010 at full severity, exactly
  as before.
- A `DROP` with no `IF EXISTS` - only the `IF EXISTS` form is the recognized
  idempotent-redefinition idiom.
- A `CREATE` that appears *before* the matching `DROP` in source order - order
  matters; that is not the redefine idiom (and still reports BW010 for the
  unpaired-looking `DROP`).
- A `DROP`/`CREATE` pair of different names, or different object kinds
  (`PROCEDURE` vs. `FUNCTION`, for example).
- `DROP TABLE ... IF EXISTS` - only `PROCEDURE`/`FUNCTION`/`VIEW` are
  redefinable objects for this idiom; a table drop is a structural change
  with its own rules (BW002 for the typed API, BW010/BW035 for raw SQL).
- The SQL text is not a compile-time constant: unknown content is not
  analyzed, per "silent when unsure".
