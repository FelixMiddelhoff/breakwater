# BW009: AddUniqueConstraint/AddPrimaryKey builds an index under lock

`migrationBuilder.AddUniqueConstraint(...)` and `migrationBuilder.AddPrimaryKey(...)`
on an existing table build the backing index while holding a lock, and the whole
migration fails if any two existing rows already collide.

## Why it hurts

- Building the index holds a lock for as long as it takes.
- The migration fails outright if any two existing rows already share a value -
  including rows an old application version keeps inserting while it does not yet
  know about the new constraint.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // breakwater: expect BW009
    migrationBuilder.AddUniqueConstraint(
        name: "AK_Users_Email",
        table: "Users",
        columns: new[] { "Email" });
}
```

## Safe alternative

Create a unique index concurrently first (outside a transaction) and verify it has
no duplicates, then attach the constraint using that index in a later migration.

## When it is fine

Lower the severity in `.editorconfig`:

```ini
dotnet_diagnostic.BW009.severity = suggestion
```

## Not reported

The constraint is on a table created earlier in the same migration: it is still
empty.
