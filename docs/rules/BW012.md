# BW012: InsertData/UpdateData/DeleteData changes many rows in one migration

`migrationBuilder.InsertData(...)`, `UpdateData(...)` and `DeleteData(...)` run as
one transaction. When the row count can be counted at compile time and is over 50
rows, Breakwater suggests batching.

## Why it hurts

A large data change inside a migration holds its lock and transaction open for as
long as the whole batch takes, which can cause lock escalation and replication lag.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // breakwater: expect BW012
    migrationBuilder.InsertData(
        table: "Countries",
        column: "Name",
        values: new object[]
        {
            "C01", "C02", "C03", "C04", "C05", "C06", "C07", "C08", "C09", "C10",
            "C11", "C12", "C13", "C14", "C15", "C16", "C17", "C18", "C19", "C20",
            "C21", "C22", "C23", "C24", "C25", "C26", "C27", "C28", "C29", "C30",
            "C31", "C32", "C33", "C34", "C35", "C36", "C37", "C38", "C39", "C40",
            "C41", "C42", "C43", "C44", "C45", "C46", "C47", "C48", "C49", "C50",
            "C51",
        });
}
```

## Safe alternative

Batch the change outside the migration, or split it across several migrations.

## When it is fine

This is a Suggestion-tier rule (`Info` severity, IDE hint only, no build output) by
default. Raise it if you want it to fail the build:

```ini
dotnet_diagnostic.BW012.severity = warning
```

## Not reported

- 50 rows or fewer.
- The row count cannot be determined at compile time (a variable-length array, a
  loop-built list): unknown counts stay silent, per "silent when unsure".
