# BW037: raw SQL creates a table or index with no IF NOT EXISTS guard

`CREATE TABLE <name> (...)` or `CREATE [UNIQUE] INDEX <name> ON <table>
(...)` inside `migrationBuilder.Sql(...)` with **no** `IF NOT EXISTS` guard
throws if the migration is ever applied a second time - a partial-deploy
retry, or two environments applying the same raw-SQL migration. This is the
structural-safety counterpart to BW036: BW036 recognizes a `DROP ... IF
EXISTS` immediately followed by a matching `CREATE` as a safe
idempotent-redefinition idiom; BW037 covers the simpler, more common case of
a bare `CREATE` with nothing to pair against.

## Design note

Scope is deliberately limited to **`TABLE` and `INDEX`** - the structural/
schema-object set matching this rule's own purpose. `PROCEDURE`/`FUNCTION`/
`VIEW` are out of scope here; that is BW036's redefinable-object set, which
already has its own DROP-then-CREATE idiom to recognize.

## Why it hurts

The typed `MigrationBuilder.CreateTable`/`CreateIndex` calls are protected
from a double-apply by EF Core's own migration-history table: a migration
that already ran is never run again. Raw SQL inside `Sql(...)` has no such
protection - if the same raw-SQL migration is re-applied for any reason
(a retry after a partial deploy failure, a manual re-run, the same script
applied against two environments), a bare `CREATE TABLE`/`CREATE INDEX`
throws because the object already exists.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // breakwater: expect BW037
    migrationBuilder.Sql("CREATE TABLE Widget (Id INT NOT NULL)");
}
```

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // breakwater: expect BW037
    migrationBuilder.Sql("CREATE INDEX IX_Widget_Name ON Widget (Name)");
}
```

## Safe alternative

Add an `IF NOT EXISTS` guard - supported by MySQL, PostgreSQL, and SQLite
for both forms:

```csharp
migrationBuilder.Sql("CREATE TABLE IF NOT EXISTS Widget (Id INT NOT NULL)");
migrationBuilder.Sql("CREATE INDEX IF NOT EXISTS IX_Widget_Name ON Widget (Name)");
```

**SQL Server has no inline `IF NOT EXISTS` form for `CREATE TABLE`/`CREATE
INDEX`.** It needs a conditional wrapper instead:

```sql
IF NOT EXISTS (SELECT 1 FROM sys.tables WHERE name = 'Widget')
BEGIN
    CREATE TABLE Widget (Id INT NOT NULL)
END
```

This rule checks for the `IF NOT EXISTS` keyword sequence regardless of
provider (it is not provider-gated the way BW019 is) - it still fires on
the bare inner `CREATE` inside a SQL Server wrapper like the one above,
since that inner statement has no `IF NOT EXISTS` of its own immediately
after `CREATE TABLE`. Treat a finding on that specific shape as a known
false positive and suppress it inline; a real parser would be needed to
recognize the wrapper form, which this tokenizer-based rule does not
attempt.

## When it is fine

Lower the severity further, or suppress with a reason, the same as any other
rule:

```ini
dotnet_diagnostic.BW037.severity = silent
```

## Not reported

- `CREATE TABLE IF NOT EXISTS`/`CREATE INDEX IF NOT EXISTS` - the guard is
  already present, which is exactly the safe form this rule asks for.
- `CREATE PROCEDURE`/`FUNCTION`/`VIEW` - out of scope; see BW036 for the
  redefinable-object idiom.
- `ALTER TABLE` statements of any kind - a different statement shape; see
  BW035.
- The SQL text is not a compile-time constant: unknown content is not
  analyzed, per "silent when unsure".
- `Sql(...)` calls inside `Down` are not analyzed (only `Up` is checked).

## Overlap with other rules

- **BW010** (TRUNCATE/DROP/unfiltered UPDATE-DELETE) never collides: none of
  its trigger keywords appear in a plain `CREATE TABLE`/`CREATE INDEX`
  statement.
- **BW035** (`ALTER TABLE` structural changes) never collides: a different
  statement shape (`ALTER`, not `CREATE`).
- **BW019** (Postgres raw SQL: `CREATE INDEX` without `CONCURRENTLY`, among
  others) *can* genuinely co-fire on the same `CREATE INDEX` statement -
  BW019 flags a missing `CONCURRENTLY` (a locking problem), BW037 flags a
  missing `IF NOT EXISTS` (a re-run-safety problem). These are two different
  hazards of the same statement, so both firing is correct, not duplicate
  noise - the same precedent as BW010 and BW034 both firing on a single
  `DROP DATABASE` statement. No suppression is registered between BW019 and
  BW037.
