# BW005: AlterColumn requires NOT NULL without a default or backfill

`migrationBuilder.AlterColumn(...)` that goes from nullable to not-null, with no
default value, is validated against every existing row: any row that already has
NULL in the column, including one an old application version is still inserting
during a rolling deploy, makes the migration fail.

## Why it hurts

- The constraint is checked against every existing row while the migration holds
  its lock.
- An old application version that does not yet know about the new constraint can
  keep inserting NULLs right up until it is retired.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // breakwater: expect BW005
    migrationBuilder.AlterColumn<string>(
        name: "Email",
        table: "Users",
        nullable: false,
        oldNullable: true);
}
```

## Safe alternative

Backfill the column in a separate migration first (or give it a default value that
covers every existing row), then constrain it to NOT NULL in a later migration.

## When it is fine

Lower the severity in `.editorconfig`:

```ini
dotnet_diagnostic.BW005.severity = suggestion
```

## Not reported

- The call also carries `defaultValue` or `defaultValueSql`: EF backfills existing
  NULLs with that default as part of the same statement.
- `oldNullable` is already `false`, or the column stays nullable.
- A column on a table created earlier in the same migration: it is still empty.
- This rule shares one `AlterColumn` call with BW004, BW015 and BW026: only the
  most specific of the four is reported for the same call.
