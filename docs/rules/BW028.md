# BW028: migration class is missing [Migration("id")] or has a duplicate id

A class deriving from `Migration` with no `[Migration("id")]` attribute is
silently skipped by EF Core's discovery. Two classes sharing the same migration id
mean only one of them ever really runs.

## Why it hurts

- A missing attribute (for example after deleting the generated `.Designer.cs`
  file) means EF Core never discovers the migration at all: the schema quietly
  diverges between environments that do and do not run it.
- A duplicate id means EF applies migrations by id order, and which of the two
  classes "wins" depends on discovery order, not on which was intended.

## Example

```csharp
using Microsoft.EntityFrameworkCore.Migrations;

// breakwater: expect BW028
public class AddNickname : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.AddColumn<string>(name: "Nickname", table: "Users", nullable: true);
    }
}
```

## Safe alternative

Add `[Migration("20260101000000_AddNickname")]` above the class (this is what
`dotnet ef migrations add` generates automatically). For a duplicate id, give each
migration its own unique id.

## When it is fine

An abstract base class shared by several concrete migrations is expected to have
no `[Migration]` attribute of its own and is not reported.

## Not reported

- Abstract classes deriving from `Migration`.
- A concrete class with a `[Migration("id")]` attribute whose id is unique in the
  compilation.

This rule looks outside `Up` by nature (at the class declaration and, for the
duplicate-id case, at every migration class in the compilation), which is why it
is one of the few exceptions to "never analyze what is not a migration Up".
