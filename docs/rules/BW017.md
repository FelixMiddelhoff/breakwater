# BW017: dropping a constraint removes a guarantee the application may rely on

`migrationBuilder.DropPrimaryKey(...)`, `DropUniqueConstraint(...)`,
`DropCheckConstraint(...)` and `DropForeignKey(...)` all remove a guarantee the
database was enforcing.

## Why it hurts

Once the constraint is gone, nothing stops rows that violate it, and an old
application version (or code that never expected the constraint to disappear) may
depend on it still holding.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // breakwater: expect BW017
    migrationBuilder.DropForeignKey(name: "FK_Orders_Customers", table: "Orders");
}
```

## Safe alternative

Confirm the constraint is really unused before dropping it, and consider keeping
the backing index if queries still rely on it even after the constraint itself is
gone.

## When it is fine

This is a Suggestion-tier rule (`Info` severity, IDE hint only, no build output) by
default. Raise it if you want it to fail the build:

```ini
dotnet_diagnostic.BW017.severity = warning
```

## Not reported

Nothing special: unlike most other rules here, this one has no "new table" or
"other argument" silence - dropping a constraint from a table created moments
earlier in the same migration is still flagged.
