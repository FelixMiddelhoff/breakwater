# BW008: AddForeignKey/AddCheckConstraint validates the whole table under lock

`migrationBuilder.AddForeignKey(...)` and `migrationBuilder.AddCheckConstraint(...)`
add the constraint already validated: EF checks every existing row while holding a
lock, which on a large table can run for a long time.

## Why it hurts

The lock is held for as long as validating every row takes, blocking other work on
the table in the meantime.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // breakwater: expect BW008
    migrationBuilder.AddForeignKey(
        name: "FK_Orders_Customers",
        table: "Orders",
        columns: new[] { "CustomerId" },
        principalTable: "Customers");
}
```

## Safe alternative

- PostgreSQL: add the constraint with raw SQL using `NOT VALID`, then run
  `VALIDATE CONSTRAINT` in a later migration.
- SQL Server: add it `WITH NOCHECK`, then run a separate `CHECK CONSTRAINT` step.

## When it is fine

Lower the severity in `.editorconfig`:

```ini
dotnet_diagnostic.BW008.severity = suggestion
```

## Not reported

The constraint is on a table created earlier in the same migration: it is still
empty, so there is nothing to validate.
