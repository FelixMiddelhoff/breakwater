# BW020: PostgreSQL DDL migration has no SET lock_timeout

A Postgres DDL operation (`DropColumn`, `AlterColumn`, `CreateIndex`,
`AddForeignKey`, ...) with no `SET lock_timeout` statement anywhere in the same
migration waits behind whatever long transaction happens to be running, and every
later query then queues behind it - an outage from a change that looked instant in
testing.

## Why it hurts

Without a `lock_timeout`, the DDL statement waits indefinitely for its lock. Once
it starts waiting, every later query on the same table queues up behind it too,
turning a small schema change into a full outage on a busy table.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    if (migrationBuilder.IsNpgsql())
    {
        // breakwater: expect BW020
        migrationBuilder.AddColumn<string>(name: "Nickname", table: "Users", nullable: true);
    }
}
```

## Safe alternative

Run `migrationBuilder.Sql("SET lock_timeout = '2s';");` (an example value) before
the DDL, and retry the migration if it times out instead of waiting indefinitely.

## When it is fine

This rule is **off by default** in every profile except `strict`, because it would
flag nearly every Postgres migration. Enable it with:

```ini
breakwater_profile = strict
```

Once enabled, lower it like any other rule:

```ini
dotnet_diagnostic.BW020.severity = suggestion
```

## Not reported

- Under the default `recommended` profile, this rule never reports.
- The call is not inside a known `if (migrationBuilder.IsNpgsql())` guard.
- The operation is not one of the DDL kinds this rule watches.
- A `Sql(...)` call anywhere in the same migration mentions `lock_timeout`.
