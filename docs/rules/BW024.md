# BW024: DeleteData removes rows that may have been edited since seeding

`migrationBuilder.DeleteData(...)`, typically generated from removing or changing
a `HasData` seed row, deletes the matching rows in every database this migration
runs against, including production rows a user has since edited.

## Why it hurts

The delete has no idea a row changed after it was seeded: it deletes by key in
every environment, including production rows a user may have since edited by
hand, with no way to tell the difference from the untouched seed row.

## Example

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // breakwater: expect BW024
    migrationBuilder.DeleteData(table: "Roles", keyColumn: "Id", keyValues: new object[] { 3 });
}
```

## Safe alternative

Confirm this is really meant to run against live data before shipping it. If the
row may have been edited, delete conditionally with raw SQL that checks the
current values first, rather than an unconditional `DeleteData`.

## When it is fine

The row is genuinely seed-only data no user can edit. Suppress it with a reason:

```csharp
// breakwater: allow BW024 lookup table, never edited by users
migrationBuilder.DeleteData(table: "Roles", keyColumn: "Id", keyValues: new object[] { 3 });
```

Or lower the severity in `.editorconfig`:

```ini
dotnet_diagnostic.BW024.severity = suggestion
```

## Not reported

Nothing special: every `DeleteData` call is reported.
